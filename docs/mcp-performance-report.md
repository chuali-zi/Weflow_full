# 聊天 MCP 读取与早报整理实验报告

实验日期：2026-10-16（UTC）。本报告只发布聚合指标、方法和代码结论；聊天正文、账号、群标识、消息引用、文章链接及本机配置保留在本地实验目录，未纳入 Git。

## 结果与采用方案

最终实现把相同预算下的全量清洗读取从 11 页降到 7 页，字符数从 847,165 降到 836,828；五轮同期读取总耗时中位数从 2.467 秒到 2.438 秒，约改善 1.2%，属于小幅变化。相对旧 compact 输出，字符数减少约 35.6%，页数减少约 36.4%。不能将减少页数直接解释成完整整理任务同比提速。

已确认作者后读取其完整一周消息，只需 1 页、97,627 字符，约为旧全群 compact 输出的 7.5%；这是缩小到用户目标作者的查询范围，原文仍完整。此步骤不包含身份发现和补查其他参与者上下文。

完成 50 次成功的读取基准和 12 次独立 Agent 整理，另有 4 次读取尝试因实时版本变化失败。四种 Agent 流程各三轮，全部保留 JSON 和可读报告。

包含失败重试的最快合格任务为 **agent-old-2，121.037 秒**；仅计算成功尝试的最快值为 **agent-clean-2-retry，118.999 秒**。后者不能替代从首次尝试起算的用户等待时间。现有样本不能证明新流程稳定将完整任务缩短到一分钟内，也不能据此声称已找到速度下限。

采用小范围分页修正和作者任务的使用指导。额外的本地排版辅助未证实提速，仅保留为实验材料，没有增加新产品工具或强制工作流。

## 任务、数据与准确性口径

固定一个已授权群，范围为北京时间 2026-10-09 09:01:47（含）至 2026-10-16 09:01:47（不含）。全群有 3,022 条消息，目标作者有 331 条。冻结查询的起止时间，每次仍读取真实 live 数据，全部成功轮次均逐条对照首次原始响应。

核心参考为六个日期的 45 条集中编号新闻。引用、发送日期和 45 个文章链接须逐项匹配，不能缺条、多条或重复；发送日期不等于文章发布日期。前次实验的两条重点补充不是完整补充清单。本轮复核完整作者原文后，将独立晨间 AI 长文、英文更新等参考扩充为 11 条；另一个通用测试数据项目公告作为可选补充，不因纳入或排除而判错。这一参考扩充发生在评分侧，未向盲测 Agent 提供条数、日期分布、标题或答案。

所有输出检查集中新闻及 11 条补充是否齐全，检查补充引用的作者、日期和链接出处。补充的链接可位于同一作者相邻两分钟内的续发消息，也可由原文不带协议的域名规范化得到；这两种情况与编造链接区分。核心 45 个链接仍要求精确匹配。

原始读取一致性检查覆盖消息顺序、完整 Unicode 正文、发送者、类型、引用、提及和媒体字段，并按 text_part 偏移拼接长消息，确认没有缺段。全量比较全部 3,022 条，作者过滤比较其全部 331 条，检查 scan_complete=true、has_more=false、omissions 为空。所有成功轮次通过。

主 Agent 逐条对照审阅了无重试快速代表轮次的 45 条摘要与原文，并复核 11 条独立补充原文。其他轮次逐项自动核对引用、日期、链接和补充覆盖，未对全部重复摘要开展独立语义复评，也没有人工评审员参与。因此“通过”指本报告规定的核对项，不等同于所有文字已获外部事实验证。未读图片、语音及链接目标正文不能被报告成已读，转贴观点、传闻与预测需保留限定。

读取总耗时从采集脚本开始到最后一页写盘，包括 MCP 连接、实际调用、响应序列化和保存。MCP 调用耗时是调用等待时间之和。字符按 JSON 的 Unicode code point 计数，不是模型 token，也不等于 Agent 实际读入上下文的 token。

默认 limit=500、max_chars=120000、direction=asc；旧工具为 read_messages(format=compact)，新工具为 read_conversation(mode=analysis, timezone=Asia/Shanghai)。每次新建 SDK Client 和 stdio 服务进程，使用同一本机已有配置，不清理操作系统磁盘缓存。同期对照交替执行；初始旧 compact 与最末版本未逐次配对，不能忽略跨阶段机器负载变化。

## Agent 完整整理（每组三次）

| 流程 | 三次成功尝试/秒 | 成功尝试中位数/秒 | 含重试中位数/秒 | 核对项通过 |
|---|---|---:|---:|---:|
| 旧工具，全量 | 128.087 / 121.037 / 525.667 | 128.087 | 128.087 | 3/3 |
| 新工具，全量 | 148.192 / 118.999 / 126.657 | 126.657 | 148.192 | 3/3 |
| 新工具，发送者过滤 | 187.029 / 138.660 / 154.001 | 154.001 | 154.001 | 2/3 |
| 发送者过滤＋本地排版辅助 | 451.206 / 468.299 / 153.597 | 451.206 | 451.206 | 3/3 |

每次使用无历史继承的独立子 Agent，继承同一父模型配置，未指定不同模型或推理档位。目标、时间范围、输出 schema 和完整性要求一致；只允许读取本轮响应及派生文件，禁止访问前次答案、评分和其他组结果。Agent 可自行解析文件。身份已在实验前确认，四组均不计身份发现时间；按作者读取组需要上下文时仍应补查，不能据作者消息推断其他人的表态。

计时从第一次实际采集开始，到写完 findings.json 和 result.md 后调用 finish。包括文件阅读、工具等待、推理及生成，排除派发之前的等待、父 Agent 评分和最终实验报告撰写。不具备真实 token、推理时间和平台排队耗时的完整分解。

独立 Agent 至多三个同时执行，以分批方式调度；没有完成严格随机化和串行隔离。因此该部分属于探索性端到端测量，不是消除并发负载、模型服务波动和缓存影响后的因果试验。第一轮全量新工具使用无投影缓存的方案 2，后两轮使用最终方案 3；响应内容相同，但计算实现不同，表中已保留该差异。

本地辅助组仍读取完整 331 条，额外使用仅处理本轮数据的脚本生成带序号的原文和字段目录。Agent 选择条目并写摘要，再由脚本带回日期、引用、标题及 URL。未预先筛选正确答案或生成摘要。该流程增加了准备、选择文件、渲染与检查步骤，实测没有证明这些步骤能缩短整个任务。

## 优化过程与最终代码

1. 方案 1 改为清洗尺寸预估，同时保留前后两次装页。页数 11→8，但中位读取时间 2.698 秒，比原清洗 2.430 秒慢约 11%。保留为反例。
2. 方案 2 将候选直接交给现有实际响应预算检查，避免重复装页，页数降到 7；重复构建整页时仍重复清洗，实测中位数 2.812 秒，未达到目标。
3. 方案 3 仅在一次 read 调用内复用相同消息对象的清洗投影。长文拆分产生新对象，重新转换；缓存不跨请求，不改变旧工具的默认行为。同期中位数 2.438 秒，对照 2.467 秒，消除了前两版明显的回退，保留减少分页的效果。
4. MCP instructions 和使用文档补充：指定作者时先确认身份、按完整范围读取作者消息，必要时补上下文；检查独立长文与英文更新，说明日期边界和不可读媒体。没有增加关键字抽样或摘要过滤。

## 检查与复核方式

最终 build:mcp（含类型检查）、test:mcp 的 40 项测试、check:mcp 的 snapshot/live 两种模式及 git diff --check 均通过。构建仅有既存 Vite 配置弃用提示。新增必要测试检查 reading/analysis 的页预算利用率、逐条正文还原，并复用 Unicode 分段、游标回放、上下文和时区检查。

本机材料位于 .runtime/ai-news-optimization/：run.cjs 负责真实 MCP 采集和完成计时，agent-task.md 保存统一任务，prepare.cjs 是辅助组排版脚本，load.cjs/audit.cjs 用于逐条还原核对，audit.json 保存各轮指标，agent-*/ 保存 Agent 答案和计时，bench-*/ 保存基准原始响应。baseline 及两版中间构建保留在忽略的 build/mcp/ 目录。运行 node .runtime/ai-news-optimization/audit.cjs 可重新核对已保存轮次。

实验数据包含私人聊天，因此没有随代码发布。其他环境复现需要自己的已授权数据、MCP 配置和独立参考清单。单个群、单个作者、同一周和三轮 Agent 样本不能推出其他任务的速度或准确性保证。本次可确认的是返回量与分页改进，以及在规定核对项下保留任务结果；稳定的端到端提速仍未得到充分证据。
