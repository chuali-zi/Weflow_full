# WeFlow MCP 产品需求草案

状态：已获用户授权进入实现。日期：2026 年 10 月 3 日。

后续设计文档：[架构设计](mcp-architecture.md)、[实现规格](mcp-spec.md)、[使用说明](mcp-usage.md)。具体参数、续读与实现约束以实现规格的细化为准。

本方案以现有提交 `170c4a9f7b930939b02ad257f8da46ee14036e24` 为基线。现有工作区在起草前已干净，基线提交与 `origin/main` 一致。需求与架构经用户确认后已进入代码实现。

WeFlow MCP 要让 Agent 从用户自然语言问题出发，准确找到群聊或私聊，用少量调用读取足够的原始材料，给出有依据的分析。核心设计是：先定位范围，再按需读取连续对话；搜索用于找线索，覆盖信息用于说明还缺什么，原文可以继续取回。

## 1 产品目标

用户应能直接说：

- 帮我看一下某某工作群有没有给我发新任务。
- 看看这周几个项目群里还有什么事情需要我处理。
- 帮我分析一下我暗恋的对象跟我现在的关系怎么样了。
- 找一下对方上次说的交付时间，后来有没有改。
- 帮我梳理我们最近一个月在聊什么，跟上个月有什么变化。

用户无需知道微信 ID、消息分库、SQL、导出格式或分页规则。Agent 应能分清谁说了什么、说给谁、何时发生、引用了哪条消息，以及是否有后续补充。

首版的成功标准是完成这些阅读和分析链路。MCP 提供事实和检索能力，调用方 Agent 负责理解用户意图和作出分析；MCP 服务自身无需配置另一个大模型。

## 2 首版范围

覆盖本机可读取的群聊和私聊、名称查找、时间范围、发送者过滤、文本搜索、连续消息分页、引用与附近上下文、消息量概览，以及可用的本机媒体。

默认使用已准备的 live 只读连接；用户显式选择 snapshot 时返回其捕获时间。不擅自修改原 profile 保存的模式。已有准备流程继续负责账号与密钥；MCP 查询不暗中扫描密钥、创建整库副本或关闭微信。

首版不加入消息发送、任务管理平台、自动催办、后台长期监控和内置情感评分。语义检索、完整语音转写和文件内容解析可以后续补充。当前无法读取的媒体必须留下占位和原因，Agent 能据此判断材料是否足够。

## 3 现有能力与需要补齐的部分

以下是仓库现状，区别于后文的拟新增能力。

| 内容 | 当前依据 | 对 MCP 的影响 |
| --- | --- | --- |
| 在线与离线读取 | Python 后端支持 live SQLCipher 与 snapshot；现有 CLI 可调用 | 复用连接和账号准备，不再做一套解密流程 |
| 会话与联系人 | 后端支持会话列表、紧凑联系人和名称映射 | 在其上增加面向 Agent 的名称匹配和消歧 |
| 消息分页 | 后端已有跨分库合并、稳定排序和游标；live 变化可使游标失效 | 封装成简短参数，并给出失效恢复方法 |
| 文本搜索 | 当前 Python 实现按会话遍历消息并作文本包含匹配 | 首版可复用有限范围搜索；不能称其为语义搜索或已优化的全局索引 |
| 消息展示与引用 | Electron ChatService 和 HTTP 映射已有正文、引用、文件等解析 | 要复用可独立调用的解析逻辑；不能只把原始 XML 包进 MCP |
| 本机图片 | 已验证本机附件定位与解密，HEIC 原图预览已接入 | 需验证独立 MCP 路径和图片内容块输出，不能直接把 GUI 验证当成 MCP 验证 |
| 其他媒体与群成员 | 内置后端尚未完整接入或验证完整群成员、视频、语音 | 状态必须区分支持、缺失与未验证；@和身份解析也需专项确认 |
| 上游 HTTP API | 已有会话、消息、联系人、群成员与媒体入口 | 可复用其映射；目前接口偏移分页和展示输出不足以覆盖本 PRD 契约 |

实现时需要新增的重点是统一输出、范围与完整性信息、正文搜索归一化、上下文补齐，以及独立于 GUI 的 MCP 入口。不能把现有 HTTP API 的每个端点直接暴露成一个工具。

## 4 首版工具清单

参数是核心契约，完整 JSON Schema 见实现规格。工具扩展为 8 个，加入完整范围文件导出；Agent 自行选择范围、格式、预算与分析方式。

| 工具 | 用途与主要输入 | 主要输出 |
| --- | --- | --- |
| `get_status` | 无业务参数；检查配置所选账号与读取模式 | 当前账号、自己身份、时间与时区、live/snapshot 状态、数据新鲜度、已验证能力和恢复动作 |
| `find_chats` | `query?`、`kind?`、`active_since?`、`limit?`、`cursor?` | 匹配的群聊/私聊、稳定 `chat_id`、展示名、备注/别名、匹配依据、最近活动；空 query 可分页浏览 |
| `get_chat_overview` | `chat_ids`、明确时间范围、`bucket?` | 所选范围的条数、收发分布、日期/周分布、媒体类型数量、可读历史边界；群成员仅返回实际可确认的身份 |
| `read_messages` | `chat_ids`、时间范围或 `after_message?`、`sender_ids?`、`types?`、`direction?`、`limit?`、`max_chars?`、`cursor?` | 按时间排序的原文、发送者与引用、覆盖范围、未返回部分、续读游标；多个会话明确保留会话归属 |
| `search_messages` | `query`、`chat_ids?`、时间范围、`sender_ids?`、`mentions?`、`types?`、`limit?`、`max_chars?`、`cursor?` | 有命中位置与命中原因的片段、稳定消息 ID、上下文锚点、搜索范围及未扫描范围 |
| `get_message_context` | `message_ids`、`before?`、`after?`、`include_replies?`、`max_chars?`、`cursor?` | 合并去重的原文窗口、被引用消息、范围内可确认的直接引用回复、未解决的引用和可扩展边界；也可按 ID 取完整正文分段 |
| `get_media` | `message_id`、`representation?` | 当前可用图片或已有可确认文本内容，媒体状态、来源和缺失原因；大媒体按需提供资源引用 |
| `export_messages` | `chat_ids`、明确时间范围、发送者/类型过滤、排序方向、输出目录 | 全范围原文 JSONL、可读 TXT 和 manifest；文件路径、状态和条数供 Agent 后续处理 |

普通业务调用不要求先执行 `get_status`，其他工具也返回最低限度的账号和新鲜度信息。连接失败或需要确认环境时才调用它，减少固定往返。

### 工具选择规则

`find_chats` 只找聊天对象，`search_messages` 只找消息线索，`read_messages` 用于连续阅读，`get_message_context` 用于围绕证据补上下文。工具描述应直接说清何时使用，并给一条典型调用例子。

不增加 `analyze_relationship` 或 `find_my_tasks` 这类直接返回结论的工具。需求、任务归属和情感判断依赖上下文，交给调用方 Agent 更透明，也避免 MCP 和 Agent 各做一遍分析。

`search_messages` 首版提供正文包含、短语和多关键词 AND/OR，明确返回 `match_mode`；输入不接受任意 SQL。语义改写由 Agent 根据问题提出，服务端不声称理解任意自然语言。对于已知会话的近期检查，直接连续读取，不能让关键词成为唯一入口。

## 5 聊天与身份定位

`find_chats` 支持昵称、备注、微信别名、群名和精确 ID。先返回精确匹配，再返回部分匹配；每个候选说明命中哪个字段。最近活动用于辅助排序，不作为确认身份的唯一依据。

唯一精确候选可直接使用；多个合理候选时给出少量可辨认的信息，让 Agent 根据已有对话线索选定，仍无法区分再向用户询问。不能把最高分候选静默当成用户所指的人。

“我暗恋的对象”这种称呼如果没有已有身份线索，MCP 不可能自行知道对象是谁。Agent 应先确认对象的姓名或备注，再定位会话。

群内发送者返回稳定身份 ID、当前可解析展示名和 `is_self`。昵称只是展示字段。旧昵称、昵称碰撞和缺失群成员映射都保留不确定状态。@以可验证的消息元数据为准；仅匹配文本姓名应标为 `name_match`，不能伪装成真实 @。

工具返回实际有消息的聊天，并区分只有联系人记录而无本机消息的候选，避免将 GUI 的联系人虚拟会话当作历史完整的会话。

## 6 消息输出契约

默认返回一个紧凑的规范化表示。每个响应只输出一次会话和参与者映射；消息引用稳定 ID，避免每条重复头像、昵称、账户目录和数据库路径。

每条消息必须保留：

- 稳定 `message_id`、`chat_id`、`sender_id`、是否由自己发送。
- 带时区的时间和稳定排序信息。同秒多条消息不能只按时间戳区分。
- 消息类型、可读原文、正文是否完整、解析状态。
- 可确认的 @身份、被引用消息 ID/引用快照、媒体和文件描述。
- 可确认的撤回/失效标记。已消失且未被记录的内容不能声称恢复。

微信长整型 server ID 以字符串传输。内部 ID 组合账号作用域、会话与可靠原始标识；没有可靠 server ID 时包含分库来源和 local ID 等必要区分信息。对外用不暴露路径的稳定标识，不能仅用 local ID 或时间戳。

默认不同时返回 raw XML、parsedContent 和重复的 content。解析出的正文、引用、链接标题/地址、文件名等作为规范字段；原始格式仅在确有需要时按 ID 取回。解析失败时返回有界原始文本与明确状态，不能悄悄变成空正文。

示例只展示消息结构，不代表已经实现：

```json
{
  "message_id": "m_example_1",
  "chat_id": "c_example_group",
  "sender_id": "p_example_manager",
  "is_self": false,
  "sent_at": "2026-10-03T09:18:00+08:00",
  "type": "text",
  "text": "小陈，明天下午三点前把方案给我。",
  "text_complete": true,
  "mentions": [],
  "reply_to": null,
  "content_status": "parsed"
}
```

群聊中的普通文字指派即使没有真实 @，也应能通过连续对话被发现。

## 7 上下文预算与完整性

有限上下文无法同时承载无限聊天和全部信息。因此产品承诺是：返回内容来源可追溯，省略明确，原文可继续读取；在限定范围和本机可读数据内，工具不得静默丢记录。不能承诺一次短响应保证语义上没有遗漏。

采用以下读取方式：

1. 定位只返回少量候选，不把全联系人列表塞给 Agent。
2. 概览在本地算日期分布和计数，帮助选时间段；概览不是聊天语义摘要。
3. 搜索先返回命中片段和可取回的 ID，明确其片段性质。
4. 连续阅读返回完整正文；超长消息分段时保留正文偏移、总长度和续读方式。
5. 上下文工具批量补齐命中窗口，合并重叠消息和相同引用。
6. 多群查询一次接受少量 chat IDs，返回各群覆盖情况。预算不足不能只返回最活跃群而让其他群无声消失。

默认值：定位 10 个候选；搜索 20 个命中；连续阅读 500 条、120,000 字符，Agent 可选 normalized/compact 格式并将预算提高到 10,000 条、2,000,000 字符。每次支持至多 5 个会话和至多 10 个上下文锚点。完整范围文件导出没有单页条数/字符预算，不额外调用模型生成摘要。字符数不声称等同于 token 数，文件完成导出不表示 Agent 已读完内容。

长消息不能因预算不足永久卡在页头：返回可继续的片段或未取回正文引用。下一页必须能继续前进，不能跳过这条消息直接称完成。

各查询统一返回应用层 `coverage`，至少包含：

| 字段 | 含义 |
| --- | --- |
| `requested_scope` | 请求账号、会话、时间区间、时区和过滤条件 |
| `scanned_scope` | 实际已扫描的会话/时间段；不能用最早最晚时间冒充中间无缺口 |
| `scan_complete` | 所选范围是否扫描完成；false 时列出尚未扫描部分 |
| `returned_count` | 实际返回的记录或片段数 |
| `has_more`、`next_cursor` | 是否还有符合条件的结果和续读入口 |
| `truncated`、`omissions` | 因预算、解析或能力边界未返回的内容及原因 |
| `unresolved_content` | 语音、图片、文件、引用等尚无法解释的记录与可取回 ID |
| `freshness` | live 查询时间/连接版本或 snapshot 捕获时间，以及实际一致性边界 |

扫描完成和返回完整分开：搜索可以扫描完但只返回前 20 个命中；也可以因为时限只扫描部分会话。计数昂贵时返回未知，不能把当前页条数当总命中数。

`coverage` 是本产品响应契约，不是 MCP 协议内置字段。客户端工具结果放入结构化输出并声明 schema；需要文本兼容回退时使用同一份紧凑表示，不额外复制一个长篇总结。结构化与文本是否都进入模型上下文需在目标客户端验收，不能假设结构化输出自动省 token。[MCP 官方工具规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)

## 8 新消息与数据变化

“新”必须有基线：用户指定时间优先；其次使用调用方保存、明确属于此账号和会话的上次检查时间/锚点；首次没有基线时默认最近 24 小时，并在答案里说明。微信未读数只作提示，不能替代这个时间范围。

首版 `read_messages` 支持从时间或完整消息排序锚点向后读，不另增一个重复的新消息工具。查询本身不推进已检查状态；调用方只有在确认读完后才可保存新的基线。再次提问不能因为上一次只是取了第一页，就把余下记录当作已检查。

翻页 cursor 与上次检查 checkpoint 是两个概念。cursor 只续读本次查询，checkpoint 只说明业务时间基线，不承诺数据库变更日志。

live 当前只能提供分库短事务的一致性，不能宣称跨库全局快照。读取初始固定时间上界，输出连接版本和读取时间；版本变化导致 cursor 失效时给出原范围和恢复锚点，Agent 重读受影响窗口并按稳定 ID 去重。时间上界不能阻止历史补入或修改，因此仍必须处理失效。

只有时间/消息锚点的增量读取无法完整发现历史补入、旧消息修改与删除。首版对近期检查重读相关窗口，并准确说明检查范围；不能声称提供可靠的全历史变更流。持久变更日志和 `get_chat_updates` 作为后续需求，确有长期监控需要时再设计。

cursor 可保留少量有界查询状态，建议闲置 10 分钟后过期并提供恢复方式。每次请求释放读事务，不为等待 Agent 保持微信数据库长事务。持续频繁变化且无法读完时必须说明未完成，可由用户选择固定 snapshot。

## 9 场景一 检查工作群新任务

用户说：“帮我看一下项目 A 工作群有没有给我发新任务。”

建议调用路径：

1. `find_chats(query="项目 A", kind="group")`，确认目标群。
2. `read_messages` 读取基线以来的连续记录，分页至该范围读完。高消息量时用 overview 决定分段，不用关键词直接排除其他消息。
3. Agent 根据指派、请求、截止时间、参与者和上下文找候选。真实 @、文字称呼、对自己上一条消息的回复、职责承接与全员通知分别判断。
4. 对前页任务继续检查后页的改期、取消、重新分配、完成和自己的答复；必要时批量 `get_message_context`，补截止时间原始约定等范围外证据。
5. 涉及图片或语音且会影响任务判定时调用 `get_media`；不可用则在答案中列出缺口。

搜索可以帮助定位“截止”“方案”等线索，但搜索不到不能成为“没有任务”的依据。

答案包含任务内容、提出者、截止时间、依据、归属明确程度，以及是否已回复/完成/取消。任务状态由可引用的对话支持；不能因为自己说“收到”就当作完成。

示例答案结构：

> 检查了昨天 18 点至今天 10 点的项目 A 群消息。发现一项明确交给你的任务：明天下午三点前提交方案，提出者是张经理。后续消息把格式改成了 PDF，你回复了“收到”，目前没看到完成确认。另有一项全组资料整理通知，是否由你负责还不明确。群里有一条语音无法读取，可能需要补充确认。

普通少量消息的目标是 2 到 4 次调用得到有依据的答案；这是验收目标，长群聊按覆盖需要继续翻页。返回“所检查范围内未发现新任务”前，应满足连续消息读完、候选任务后续状态已检查；有未解媒体时明确限定结论。

## 10 场景二 分析私聊关系变化

用户说：“帮我分析一下我暗恋的对象跟我现在的关系怎么样了。”

先从已知姓名/备注定位对象；没有线索时确认身份。时间范围优先采用用户指定；未指定时建议最近 30 天，并取相邻的前 30 天作为对照，明确这是起始分析范围。可读历史不足时直接说明，不编造更长时间线。

建议调用路径：

1. `find_chats` 定位私聊。
2. `get_chat_overview` 看近期与前期的日期分布、收发数量和媒体缺口。
3. `read_messages` 读近期连续对话，按实际消息量分页；历史对照先按日期分布选择多个连续窗口，明确这是抽样，再视结论补读。
4. 对邀约、拒绝、关心、争执和关系讨论等证据用 `get_message_context` 补前因后果；同时检查支持与反对当前判断的材料。

首版 overview 可给确定性计数；“主动开启话题”“回复速度”“对话结束”等依赖定义的统计先由 Agent 谨慎分析，若后续增加工具统计，需说明如何处理跨日、连续发送与长间隔。不得把消息数量直接换算成喜欢程度。

首版不让 MCP 自动生成情感摘要或选择所谓“最暧昧消息”。Agent 应关注双方投入、回应是否有内容、是否主动延续话题、邀约是否落实、是否表达边界，以及这些行为与之前有何变化。

答案分清可观察事实、合理解释和暂时无法判断的部分，引用代表性原文，同时呈现反例。只读了一部分历史就要说是有限窗口观察；不能凭搜索抽样声称读完全部关系史，也不输出“喜欢你 87%”这类无依据数值。

轻量私聊目标约 4 到 6 次调用获得第一版有依据的观察。历史长、消息密集时允许多次分段阅读和调用方保存阶段笔记，笔记保留原始消息 ID，不能代替后续必要原文。

## 11 检索性能与实现方向

建议独立本地 MCP 进程，默认 stdio，由客户端启动；可在 GUI 未运行时读取已经准备好的账号。查询服务保持一个后端连接，避免每次调用都启动整套 CLI。源码入口和安装包入口复用现有后端发现与运行方式。

拟采用 TypeScript MCP 适配层，复用 Python 后端 RPC；把现有可独立复用的正文/引用/类型映射提取为普通模块，供 MCP 和现有入口共享。若实现前确认提取成本过高，再比较 Python 入口的必要适配量；选择依据是少重复和容易打包，协议层使用官方 SDK，不手写整套协议。

逻辑链路：调用方 Agent → MCP 参数与结果适配 → 名称定位和消息归一化 → 现有 Python 只读查询后端 → 微信本机数据库。

原 HTTP API 可以作为补充适配入口；默认独立运行方案不要求用户一直打开 GUI 或额外启用 HTTP 服务。审核后先完成连接和解析复用验证，再确定具体拆分文件。

stdio 是首版交付传输；未来确有本机 HTTP 接入需求时按 Streamable HTTP 规范增加适配。已有 WeFlow SSE 消息推送不等同于 MCP 传输。[MCP 官方传输说明](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports)

性能顺序：

1. 先做时间/会话限界和批量调用，把 SQL 可执行的过滤下推，并复用有界缓存。
2. 复用当前游标与跨库合并逻辑，避免无界 offset 扫描。
3. 搜索匹配规范化正文，解析长文本；记录实际扫描范围，超时返回可恢复状态，不假报零结果。
4. 用合成和授权的实际账号测量。若全局文本搜索无法满足目标，再增加可重建的本地正文索引，明确已索引范围及源数据版本；首版不默认复制全库建向量库。

拟定性能目标：已准备并预热的本机连接下，常规定位/50 条短阅读 P95 在 1 秒内，单会话 30 天文本搜索 P95 在 2 秒内。搜索/概览在约 4.2 秒扫描工作时间后返回已有结果和续扫入口；大块原文读取使用约 20 秒，文件导出连续执行并报告进度。上述性能目标不是现有性能承诺；测试报告记录硬件、数据量、冷/热状态。

服务端本地可以扫描比返回量更多的记录、合并窗口、统计计数；语义结论仍由 Agent 根据读到的原文作出。既减少返回冗余，也保留必要材料。

## 12 连接与必要边界

用户准备好 WeFlow 后，首版应提供一段可直接复制的 MCP 客户端配置，并支持源码与安装版。连接异常返回可操作的错误：目标账号未确定、profile 锁定、密钥未准备、snapshot 过旧、数据库忙、游标失效、能力不可用等。

一个服务实例固定一个已选择的 profile 和账号，查询工具不随意跨账号。多账号启动时明确选择，避免分析到另一个人的聊天。headless 连接遵守现有 profile 应用锁规则；不能把 GUI 曾经解锁解释成独立进程自动获得权限。

工具描述声明读取行为，但标注只是客户端提示；底层仍使用只读连接。密钥、Token 和数据库绝对路径不进入聊天工具结果。普通日志保留耗时、数量和错误，默认不记录正文。

聊天正文作为被检索的数据返回，其中的“忽略之前指令”等文字不能变成服务端命令或扩大查询范围。这一点通过固定工具参数和数据输出边界实现，不为普通阅读增加反复确认流程。是否调用云模型由用户选择的 Agent 客户端决定，本地 MCP 不能承诺聊天永远不离开本机。

## 13 验收场景

审核后只做能证明核心行为的必要验收，使用合成聊天覆盖边界，真实账号内容不写入仓库。

| 场景 | 应达到的结果 |
| --- | --- |
| 私聊备注和昵称、两个同名群 | 正确匹配唯一目标；歧义返回候选与依据，不静默选错 |
| 群任务没有 @，只称呼本人 | 连续阅读仍保留任务和可确认的身份线索 |
| 前页安排任务，后页取消/改期 | 最终答案采用后续状态并引用两处证据 |
| 指定范围内文本零命中但有语音 | 明确文本结果与未解媒体，不能断言绝对没有任务 |
| 暧昧词很少但对方主动邀约 | 连续对话能提供材料，关系分析不依赖关键词命中 |
| 关系样本同时有积极和拒绝信息 | 支持和反对证据都可取回；抽样范围有明确标记 |
| 同秒多消息、跨库 ID 与长整型 | 无精度丢失，分页不漏、不重复，消息可稳定取回 |
| 超长文本及多个重叠上下文窗口 | 分段可恢复，窗口去重，引用身份和取消/否定原文保留 |
| live 阅读时变更或历史补入 | 返回失效/变化信息和恢复范围，不声称固定全局快照 |
| 多群查询达到预算或扫描超时 | 每群明确完成状态，未扫范围可继续，不把当前页视作全部 |
| snapshot 查询新任务 | 显示捕获时间，答案说明其时效限制 |
| 图片缺失、群成员未知、profile 锁定 | 给出真实状态和恢复动作，不编造媒体内容或身份 |

两个主场景各用一组已知答案的聊天 fixture 验收：Agent 能定位目标、读取必要原文、解释覆盖边界并给出引用。补充一次目标 MCP 客户端联调，确认工具列表、输出渲染、正文预算、图片与错误恢复。

上下文成本以实际客户端测量，比较相同场景的规范化结果与现有 raw/XML 重复结果。目标是明显减少冗余，所有已返回证据仍能按 ID 查回。先测量，再给出节省比例。

## 14 审核后的实施顺序与待确认选择

建议按以下顺序实施：

1. 验证独立进程连接、现有 profile 规则和正文/引用解析复用，确定实际可交付的媒体范围。
2. 完成定位、连续阅读、概览、搜索、上下文工具与覆盖契约；打通两个主场景。
3. 加入按需媒体入口、客户端配置和安装包入口，做必要联调与性能测量。
4. 根据真实使用瓶颈决定是否需要正文索引、可靠变更增量或语音转写。

本草案建议审核的核心选择是：

- 当前提供上述 8 个工具，包括紧凑大块阅读和完整范围文件导出；任务和关系分析由外部 Agent 完成。
- 首版默认独立 stdio 运行，复用已准备的账号，不依赖 GUI 常开。
- 任务首次检查默认最近 24 小时；关系分析默认最近 30 天及前 30 天对照，始终说明实际范围。
- 文本与引用优先完整；本机图片按能力接入，无法读取的语音/文件明确标记。若要求第一版覆盖语音和截图中的任务，则把转写/OCR 提升为首版必要范围，调整交付顺序。
- 节省上下文依靠范围、分层读取、去重和可恢复原文；不把无法证明的“自动无损摘要”当承诺。

上述均为方案建议，等待用户审核后进入实现。
